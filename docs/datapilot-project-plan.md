# DataPilot 项目严格执行计划

## 1. 项目身份

- GitHub 仓库名：`datapilot-ai-data-analysis-agent`
- 项目展示名：`DataPilot：本地自然语言数据分析 Agent`
- 目标岗位：AI 应用开发工程师
- 当前状态：阶段 11 已完成，阶段 15 已补充失败案例记录和真实首页截图；完整上传后的结果截图及阶段 16 独立复述仍待完成。已接入计划执行、工具结果展示、基于真实证据的中文报告、Plotly 图表、CSV/PNG/Markdown 导出和 20 条固定中文评估集
- 当前负责人：独立开发
- 参考项目：[`Shubhamsaboo/awesome-llm-apps`](https://github.com/Shubhamsaboo/awesome-llm-apps) 中的 `starter_ai_agents/ai_data_analysis_agent`
- 本项目与 LearningHub 的区别：LearningHub 解决中文文档知识库检索和来源约束问答；DataPilot 解决结构化业务数据的自然语言分析和受控工具调用。

## 2. 最终目标

用户上传一份中文电商经营数据 CSV 或 XLSX 文件，用自然语言提出问题，例如“哪个地区销售额最高”“最近几个月的订单量有什么变化”“哪些商品需要关注”。系统由本地 Ollama 模型生成结构化分析计划，再由受控工具执行数据概览、只读 SQL、分组统计、异常检测和图表生成，最后根据真实工具结果生成中文分析结论。

最终成果必须满足：

1. 能在本地启动并完成一次完整分析流程。
2. 不允许模型直接执行任意 Python、系统命令或写入型 SQL。
3. SQL 只能访问当前上传的数据表，并且只允许只读语句。
4. 模型输出必须先经过结构化校验，计划不合格时不能直接执行。
5. 每个结论都能回溯到执行过的工具、SQL 或统计结果。
6. 本地模型不可用时，页面要给出清楚的失败信息，不伪造分析结果。
7. 测试、评估问题、运行说明和项目限制必须与真实实现一致。

## 3. 上游项目拆解

### 3.1 保留的思路

- Streamlit 工作台形态，便于快速验证上传、提问和结果展示。
- Pandas 负责文件读取和基础数据处理。
- DuckDB 负责将表格数据转换为可查询的数据表，并执行分析 SQL。
- Agent 根据用户自然语言调用数据分析工具。
- 图表和数据表作为分析结果的一部分展示。

### 3.2 必须替换的内容

- 云端 OpenAI GPT-4o：替换为本地 Ollama，并支持 `qwen2.5:3b`、`qwen3:4b` 等已安装模型。
- 英文通用演示：替换为中文电商经营数据和中文问题。
- 模型自由生成代码：替换为固定工具集合和结构化分析计划。
- 无边界 SQL：替换为只读 SQL 校验、表名限制、结果行数限制和超时控制。
- 单文件快速演示：拆分为配置、数据处理、查询安全、工具、Agent 编排和界面模块。
- 缺少验证：增加单元测试、接口级测试、固定评估问题和安全拦截案例。

### 3.3 暂不照搬或暂不实现

- 不使用云端 API 作为默认路径。
- 不允许 Agent 执行任意 Python 代码。
- 不接入真实企业数据库、生产数据或外部系统。
- 不宣称生产级权限系统、分布式部署、实时数仓或高准确率。
- 不在没有测试和真实运行记录前填写准确率、性能指标或用户数量。

## 5. 严格阶段计划

每个阶段完成后必须执行该阶段的验收项，并在 `docs/decision-log.md` 增加真实记录。未通过验收时，只修复当前阶段，不提前堆叠下一阶段功能。

### 阶段 1：上游分析与边界冻结

目标：先理解参考项目，再确定 DataPilot 的改造边界。

执行内容：

1. 记录上游项目的入口文件、依赖、运行方式和核心调用链。
2. 画出“上传文件 -> Agent -> SQL -> 结果展示”的原始流程。
3. 列出保留、替换、删除和新增项。
4. 明确本地 Ollama 的接口形式、模型选择方式和失败路径。
5. 明确第一版只支持 CSV/XLSX 和单个数据集。

产物：项目 README、选型日志、目标架构图、本计划。

验收标准：能够用自己的话解释 Streamlit、DuckDB、Agent 和工具调用分别负责什么；不能只说“参考了 GitHub”。

禁止事项：不复制上游代码后直接改标题；不把上游项目的能力写成自己的已完成成果。

### 阶段 2：项目骨架与独立依赖

目标：建立可以单独安装、测试和运行的项目目录。

计划结构：

```text
projects/03-data-analysis-agent/
├── app.py
├── config.py
├── requirements.txt
├── README.md
├── data/
│   └── sample_ecommerce.csv
├── src/
│   ├── models.py
│   ├── data_loader.py
│   ├── data_quality.py
│   ├── sql_guard.py
│   ├── query_engine.py
│   ├── tools.py
│   ├── planner.py
│   ├── report_generator.py
│   └── chart_service.py
└── tests/
    ├── test_data_loader.py
    ├── test_data_quality.py
    ├── test_sql_guard.py
    ├── test_tools.py
    ├── test_planner.py
    └── test_report_flow.py
```

执行内容：

1. 先创建独立 `requirements.txt`，只加入实际需要的依赖。
2. 验证 `agno`、`duckdb`、`openpyxl`、`plotly`、`kaleido`、`httpx`、`pydantic` 的安装和导入。
3. 固定 Python 版本说明和 Windows 启动命令。
4. 创建最小可运行的 Streamlit 页面，但暂不接入模型。

验收标准：空页面可以启动；依赖可以在全新虚拟环境中安装；测试命令能被执行。

### 阶段 3：构造可复现中文样例数据

目标：用可解释、无隐私的电商数据支撑演示和测试。

执行内容：

1. 设计字段：订单日期、地区、渠道、商品类别、商品名称、数量、单价、折扣、销售额、成本、客户类型和订单状态。
2. 生成 CSV，并额外生成 XLSX 版本验证两种读取路径。
3. 使用固定随机种子，保证每次生成结果一致。
4. 人工加入少量可解释的高值订单、缺失值、重复订单和异常金额，用于质量检查演示。
5. 写明数据是合成样例，不代表真实企业经营数据。

验收标准：样例文件可打开；字段含义有说明；固定问题可以得到可验证的预期结果；不包含真实个人信息。

### 阶段 4：文件读取、编码与类型识别

目标：可靠读取 CSV/XLSX，并拒绝不受支持的输入。

执行内容：

1. 限制扩展名为 `.csv` 和 `.xlsx`。
2. 限制文件大小和最大行数，具体数值以实际测试后记录。
3. CSV 按 UTF-8、GBK 等有限编码顺序尝试，并记录最终使用的编码。
4. 清理列名空格、重复列名和不可用列名。
5. 识别日期、数值和文本列，保留原始值与转换失败记录。
6. 对空文件、无表头文件、损坏文件、超大文件给出中文错误信息。

验收标准：正常 CSV/XLSX、中文编码 CSV、空文件、损坏文件和超限文件均有测试；失败时页面不会显示旧文件的结果。

### 阶段 5：数据概览与质量检查

目标：先让用户看懂数据，再允许 AI 分析。

执行内容：

1. 展示行数、列数、字段类型和示例行。
2. 统计每列缺失值、唯一值、重复行和数值范围。
3. 标记疑似金额、日期、分类和 ID 字段，但不擅自修改业务含义。
4. 对重复订单、负数金额、空日期等问题输出警告。
5. 将数据质量结果作为 Agent 可读取的上下文之一。

验收标准：至少覆盖正常数据、含缺失值数据、含异常数值数据；统计结果与 Pandas 直接计算一致。

### 阶段 6：DuckDB 只读查询与 SQL 安全

目标：让自然语言分析可以调用 SQL，同时建立清晰的安全边界。

执行内容：

1. 将当前 DataFrame 注册为受控表名，例如 `uploaded_data`。
2. 只允许 `SELECT` 或明确允许的只读查询语句。
3. 拦截 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`CREATE`、`COPY`、`INSTALL`、`LOAD`、多语句和系统表访问。
4. 校验查询只能访问当前上传表及允许的临时对象。
5. 限制返回行数、查询时间和结果大小。
6. 对 SQL 语法错误返回可理解的错误，不把数据库堆栈直接展示给用户。
7. 记录执行 SQL、耗时、行数和状态，但不记录隐私数据。

验收标准：合法查询可执行；所有写入型 SQL 和危险关键字都有测试；多语句、注释绕过、未知表名和超限结果被拦截。

禁止事项：不能用字符串替换假装完成安全校验；不能让模型传入任意 Python 表达式；不能把 SQL 安全等同于“模型说它是安全的”。

### 阶段 7：受控工具与 Pydantic 契约

目标：将分析能力拆成可测试、可审计的工具。

计划工具：

- `get_data_overview`：返回字段、行数、类型和质量摘要。
- `run_readonly_sql`：执行经过安全校验的只读 SQL。
- `group_by_summary`：按指定维度计算数量、金额、均值或占比。
- `detect_anomalies`：按明确规则找出异常订单或异常数值。
- `build_chart`：根据结构化结果生成图表配置或图片。

执行内容：

1. 为每个工具定义 Pydantic 输入和输出模型。
2. 对字段名、聚合函数、排序方向、行数和图表类型做白名单校验。
3. 为每次调用生成工具记录，包括工具名、输入摘要、状态、错误和结果摘要。
4. 工具返回结构化数据，不直接返回无法解析的大段自然语言。

验收标准：工具可以脱离 LLM 单独测试；非法参数无法进入查询引擎；工具错误能被上层识别。

### 阶段 8：接入 Ollama 本地模型

目标：完成离线模型调用，并支持页面选择可用生成模型。

执行内容：

1. 检测 Ollama 服务是否可用。
2. 获取本机已安装模型，过滤掉仅用于 Embedding 的模型。
3. 默认使用 `qwen2.5:3b`，支持切换 `qwen3:4b` 等已安装模型。
4. 设置请求超时、温度和最大输出长度，并通过配置集中管理。
5. 处理服务未启动、模型不存在、超时、返回空内容和非 JSON 响应。
6. 页面明确显示模型状态，不把降级结果伪装成本地模型结果。

验收标准：Ollama 正常时可以收到真实模型响应；模型不可用时有可复现的错误提示；没有模型时页面仍可查看数据概览。

### 阶段 9：结构化分析计划、校验与修复

目标：让模型先提出受控计划，再执行工具。

计划 JSON 至少包含：用户目标、步骤列表、每步工具名、工具参数、预期输出和最终报告重点。

执行内容：

1. 用 Pydantic 定义分析计划 schema。
2. Prompt 要求模型只输出 JSON，不执行代码，不虚构结果。
3. 解析 Markdown 代码块、额外说明和非法 JSON，并统一返回解析错误。
4. 校验工具名、字段名、聚合函数、SQL 只读性、步骤数量和参数范围。
5. 对可修复的格式错误最多发起一次修复请求。
6. 修复后仍不合格时停止执行并展示原因。

验收标准：合法计划可以执行；非法工具、未知字段、危险 SQL 和缺失参数会在执行前被拦截；修复次数不会无限循环。

### 阶段 10：工具执行记录与中文报告

目标：让最终回答基于真实执行结果，并能够解释分析过程。

执行内容：

1. 按计划顺序执行工具，任一步失败时记录并决定是否终止。
2. 保存每一步的工具名、参数摘要、返回摘要、耗时和错误状态。
3. 将工具结果、质量警告和用户问题传给报告模型。
4. 要求报告区分事实、推断、建议和数据限制。
5. 报告中引用结果来源，例如“基于步骤 2 的分组统计”。
6. 证据不足时输出“当前数据无法支持该结论”，不能自行补充数据。

验收标准：页面能看到分析步骤和最终报告；报告数值来自工具结果；工具失败或数据不足时不会输出伪造结论。

### 阶段 11：Plotly 图表与导出

目标：把分析结果转成用户可检查、可保存的产物。

执行内容：

1. 支持至少柱状图、折线图和饼图或散点图中的三类。
2. 图表标题、坐标轴和图例使用中文，并与实际字段一致。
3. 图表只接收结构化结果，不允许模型直接写 JavaScript。
4. 提供 CSV、PNG 和 Markdown 报告导出，具体格式以依赖验证为准。
5. 处理空结果、类别过多、负值和中文字体问题。

验收标准：固定评估问题至少有两类图表能正确生成；下载内容与页面显示结果一致；图表失败不会阻断文字报告。

### 阶段 12：中文 Streamlit 工作台

目标：形成适合面试演示的完整中文交互界面。

页面区域：

1. 文件上传与当前数据集状态。
2. 数据概览和质量检查。
3. 模型选择和 Ollama 状态。
4. 自然语言提问区。
5. 分析计划和工具执行过程。
6. 结果表格、图表、报告和导出按钮。
7. 错误、加载中、空数据和重置状态。

验收标准：中文文案统一；上传新文件后旧结果清理；重复提问状态正确；异常状态不遮挡主要内容；至少验证桌面窗口尺寸。

### 阶段 13：测试体系

目标：用测试证明关键边界，而不是只靠手动截图。

最低要求：至少 25 项测试，按真实实现调整数量，但不能为了凑数复制同类断言。

覆盖范围：

- CSV/XLSX 正常读取。
- 中文编码处理。
- 空文件、损坏文件和超限输入。
- 列名清洗和类型识别。
- 数据质量统计。
- 合法只读 SQL。
- 写入型 SQL、危险关键字、多语句和未知表拦截。
- 工具参数校验和错误返回。
- 结构化计划解析、非法计划拒绝和一次修复上限。
- Ollama 正常响应、超时、空响应和模型不存在。
- 报告基于工具结果生成。
- 图表空结果处理。
- 页面关键交互或最小启动检查。

验收标准：测试在没有 Ollama 的环境中仍能运行大部分单元测试；依赖模型的测试使用 mock，不把本机偶然状态当作测试通过条件。

### 阶段 14：固定评估集

目标：对 Agent 分析结果进行可重复的人工和程序评估。

执行内容：

1. 编写 20 条中文固定问题，覆盖总量、分组、趋势、异常、组合条件、无关问题和无法回答问题。
2. 为每条问题记录预期工具、关键字段、预期结果范围和是否应该拒答。
3. 记录计划是否正确、工具是否正确、数值是否正确、图表是否合理和是否越权。
4. 区分“模型回答质量”和“系统安全行为”，不把主观评价伪装成准确率。
5. 只在真实运行后记录结果和环境信息。

验收标准：评估集可重复运行；每个问题都有明确判断标准；结果中保留失败案例及原因。

### 阶段 15：文档、截图与简历材料

目标：把可运行项目整理成能展示、能复述的简历项目。

执行内容：

1. README 用中文写清楚背景、架构、安装、启动、示例问题、限制和测试。
2. 加入一张不含个人隐私和密钥的真实运行截图。
3. 写项目总结：需求、关键难点、技术取舍、失败处理和后续计划。
4. 根据真实完成内容生成简历项目描述，禁止提前写未完成能力。
5. 准备面试问答：为什么不用 RAG、DuckDB 做什么、Agent 与普通调用有什么区别、SQL 如何限制、模型失败怎么办。

验收标准：另一台电脑按 README 能完成安装和启动；用户能逐条解释简历中的技术名词；文档与代码、测试和截图一致。

### 阶段 16：独立复述与简历准入

目标：确保项目是用户真正理解过的作品，而不是只会启动的代码。

准入问题至少包括：

1. Streamlit 与 FastAPI 在两个项目中的职责差异。
2. DuckDB 为什么适合本地分析。
3. Agent、工具调用和结构化计划之间的关系。
4. 为什么不让模型执行任意 Python。
5. 只读 SQL 如何拦截危险操作。
6. Pydantic 校验解决什么问题。
7. Ollama 不可用时系统如何处理。
8. 如何验证一个分析结果不是模型编造的。

验收标准：用户可以不看代码讲清完整链路，并能根据日志定位一次失败；在此之前，简历只写“开发中”或不写入正式项目经历。
